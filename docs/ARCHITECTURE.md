## 2. 인프라 흐름

### 쓰기 경로 (분석 파이프라인 → R2)

```
1. GitHub Actions 러너 또는 Hetzner VPS 시작 (에페머럴)
2. Python 의존성 설치 (캐시 활용)
3. 파이프라인 실행: 수집 → 스크리닝 → 스코어링 → 랭킹 → SQLite 작성
4. boto3로 R2 인증 (S3 호환 엔드포인트)
5. valueforge.db → R2 키 latest.db (덮어쓰기)
6. valueforge.db → R2 키 history/YYYY-MM-DD.db (복사)
7. 7일 이상된 history/*.db 키 삭제
8. latest_metadata.json R2에 작성
9. 러너 종료 (VM 자동 소멸)
```

### 읽기 경로 (Streamlit → R2 → 사용자)

```
1. 사용자 Streamlit Cloud URL 접속
2. @st.cache_resource(ttl=1800) 캐시 유효성 확인
3. 캐시 만료 시: boto3로 R2의 latest.db → /tmp/valueforge.db 다운로드
4. SQLite 연결 (읽기 전용)
5. 쿼리 실행, 결과 렌더링
```

## 3. 데이터 파이프라인 흐름

### 스케줄러 흐름

```
[GitHub Actions Cron: "0 8 * * 1-5"]
= 08:00 UTC = 17:00 KST
= 장 마감 후 약 1시간 30분

Step 1: actions/checkout@v4
Step 2: actions/setup-python@v5 (Python 3.11)
Step 3: pip install -r requirements.txt (캐시)
Step 4: python -m src.pipeline.runner
        │
        ├─ 수집: pykrx (30-60분, 전 종목)
        ├─ 수집: DART 재무 데이터 (15-30분)
        ├─ Stage 1 필터 (< 1분)
        ├─ Stage 2 스코어링 (< 2분)
        ├─ Stage 3 함정 감지 (< 1분)
        ├─ Stage 4 랭킹 (< 1분)
        ├─ SQLite 작성 (< 1분)
        └─ R2 업로드 (< 2분)

총 실행 시간: 약 60-90분
```

> **중요**: GitHub Actions 무료 티어는 월 2,000분. 90분 × 22거래일 = 1,980분으로 매우 빠듯하다.  
> **권장**: 제약 없는 Hetzner CX11 VPS ($3.29/월) 사용. → [DEPLOYMENT.md](DEPLOYMENT.md) 참조

### 스크리닝 우주 축소

```
전체 종목 (~2,600개)
       │
       │ Stage 1: 빠른 필터
       ▼
약 400-700개 (명백한 비가치 종목 제거)
       │
       │ Stage 2: 심화 스코어링
       ▼
약 400-700개 (복합 점수 산출)
       │
       │ Stage 3: 가치 함정 감지
       ▼
약 300-600개 (함정 플래그/제거)
       │
       │ Stage 4: 최종 랭킹
       ▼
상위 50-100개 (복합 점수 기준 정렬)
```

## 4. SQLite 생명주기

```
파이프라인 시작
     │
     ▼
/tmp/valueforge_YYYYMMDD.db 신규 생성
     │
     ▼
스키마 적용 (CREATE TABLE IF NOT EXISTS)
     │
     ▼
stocks, prices, fundamentals 벌크 INSERT
     │
     ▼
스크리닝 파이프라인 실행 (인메모리 또는 SQLite 쿼리)
     │
     ▼
scores, risk_flags, rankings, pipeline_runs 작성
     │
     ▼
VACUUM + ANALYZE (파일 크기 최소화, 쿼리 플래너 최적화)
     │
     ▼
R2 업로드: latest.db + history/YYYY-MM-DD.db
     │
     ▼
로컬 임시 파일 삭제
     │
     ▼
[파이프라인 종료]

Streamlit 시작 시:
     │
     ├─► R2에서 latest.db 다운로드 → /tmp/valueforge.db
     └─► SQLite 연결 (읽기 전용)
          └─► st.cache_resource에 유지 (30분 TTL)
```

## 5. 장애 복구 흐름

| 장애 유형                      | 동작                                                                                |
| ------------------------------ | ----------------------------------------------------------------------------------- |
| pykrx API 타임아웃             | 3회 재시도 (지수 백오프); 최대 재시도 초과 시 해당 종목 건너뜀, 로그 경고           |
| DART API 레이트 리밋           | 60초 대기 후 재시도; DART는 일 10,000건 허용으로 드문 상황                          |
| 개별 종목 데이터 누락          | 해당 종목 건너뜀, 로그 기록, 파이프라인 계속 진행                                   |
| 전체 수집 실패 (50% 미만 수집) | 파이프라인 전체 실패 처리; 기존 latest.db 유지 (덮어쓰지 않음)                      |
| R2 업로드 실패                 | 3회 재시도; 실패 시 GitHub Actions 이메일 알림; 부분 결과로 latest.db 덮어쓰지 않음 |
| 한국 장 휴장일                 | `is_trading_day()` 체크 후 exit(0)으로 graceful 종료                                |

## 6. 아키텍처 결정 및 트레이드오프

| 결정         | 선택               | 근거                                                   | 트레이드오프                                           |
| ------------ | ------------------ | ------------------------------------------------------ | ------------------------------------------------------ |
| 데이터베이스 | SQLite             | 서버 비용 0, 파일 이식성, 읽기 중심 대시보드에 충분    | 동시 쓰기 불가; 일 1회 배치 쓰기이므로 문제없음        |
| 스토리지     | Cloudflare R2      | 무료 티어 넉넉 (10GB), S3 호환 API, 이그레스 비용 없음 | 약간의 레이턴시; 허용 범위                             |
| 프론트엔드   | Streamlit Cloud    | 비용 0, Python 네이티브, 빠른 구축                     | React 대비 커스터마이징 제한; MVP에는 충분             |
| 스케줄러     | Hetzner VPS + cron | 분당 제약 없음, 영구 VM, 저렴                          | 월 $3.29 비용; GitHub Actions 대비 관리 부담 소폭 증가 |
| 수집         | pykrx + DART       | 공식 한국 시장 데이터, 무료, 잘 유지됨                 | DART 등록 필요; pykrx는 스크래핑 기반                  |
| 재무 데이터  | DART OpenAPI       | 공식 금융감독원 공시 데이터, 구조화됨, 무료            | API 키 필요; 분기 공시 지연 발생 가능                  |
| 분석 위치    | 에페머럴 서버      | 상시 운영 비용 없음, 매 실행마다 클린 환경             | 콜드 스타트 시간; 일 1회 배치에는 문제없음             |

### SQLite를 전송 레이어로 사용하는 이유

단일 SQLite 파일이 파이프라인과 대시보드 간의 인터페이스다. 이 패턴은:

- API 서버 불필요 (복잡도 제거)
- R2 → Streamlit 간 단순한 파일 전송
- 대시보드에서 임의 SQL 쿼리 가능 (사전 정의 API 엔드포인트 불필요)
- 파워 유저가 SQLite 파일을 직접 다운로드하여 자체 분석 가능
